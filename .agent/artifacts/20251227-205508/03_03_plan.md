# Implementation Plan

## Overview
Fix the messageContent parsing issue by modifying the write side (adapter.go) to serialize MessageContent to JSON using sonic.Marshal (which calls the custom MarshalJSON method), and updating the read side (dashboard_repo.go) to deserialize JSON back to MessageContent with sonic.Unmarshal, with backward compatibility for existing plain-text records. Use lo.ToPtr for cleaner pointer creation.

## Architecture Decisions

### Decision 1: Use bytedance/sonic for JSON Serialization
**Choice**: Use `sonic.Marshal` and `sonic.Unmarshal` for JSON serialization in adapter.go and deserialization in dashboard_repo.go
**Rationale**:
- The daemon and cli modules already use `bytedance/sonic` for JSON operations
- `sonic.Marshal` correctly calls the custom `MarshalJSON()` method on `MessageContent`, so the existing serialization logic is preserved
- `sonic.Unmarshal` correctly calls the custom `UnmarshalJSON()` method on `MessageContent`, so the existing deserialization logic is preserved
- Provides better performance than `encoding/json`
- Ensures consistency across the codebase

### Decision 2: Use samber/lo for Pointer Creation
**Choice**: Use `lo.ToPtr()` instead of inline pointer creation for the backward compatibility fallback
**Rationale**:
- Cleaner syntax: `lo.ToPtr(content)` vs `func() *string { s := content; return &s }()`
- Already used in the cli module (`cli/internal/service/tracking/tracking_service.go`)
- Type-safe generic function that works with any type

### Decision 3: Store JSON String for All MessageContent Types
**Choice**: Always serialize `MessageContent` to JSON string regardless of `IsBlocks` value
**Rationale**: This creates a unified storage format. Text content like `"hello"` becomes the JSON string `"\"hello\""`, and block content becomes a JSON array `"[{\"type\":\"tool_use\",...}]"`. The existing `MessageContent.UnmarshalJSON()` handles both formats correctly.

### Decision 4: Backward Compatibility via Fallback Parsing
**Choice**: On read, attempt JSON unmarshal first; if it fails, treat content as legacy plain text
**Rationale**: Existing records stored plain text directly (not JSON-encoded). The fallback ensures these records remain readable while new records use the proper JSON format.

### Decision 5: Non-Fatal Error Handling on Write
**Choice**: Log warnings on serialization failure but do not fail the entire batch
**Rationale**: A single message serialization failure should not prevent other valid records from being stored. This aligns with the existing logging patterns in the codebase.
